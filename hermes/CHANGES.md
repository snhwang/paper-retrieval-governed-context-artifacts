# WP7 Hermes materials: what we changed and why

This directory holds the materials for the execution-level experiment (WP7) of the TIST revision. They run Hermes Agent v0.22.2 (commit `d923a5eb`) and its harness `evals/core_tool_deferral` under BEAR's Hermes plugin (built on bear-dev `90daeb9`, and run from stage 1 on `10730c8`, which reports 0.4.0). This file lists every change we made to the harness and why. Nothing in the Hermes tree is edited. The worker is generated from the harness's own `worker.py` by anchored replacements, and the full diff is at the end.

## Worker

`worker/worker_local.py` is generated by `worker/make_worker_local.py` from `evals/core_tool_deferral/worker.py`. Each anchor must match exactly once, so an upstream change fails the generator instead of drifting. Every edit applies to every arm alike. The arm is chosen only by the HERMES_HOME `config.yaml` the runner writes per cell.

| Edit | What | Why |
| --- | --- | --- |
| E1 | `HARNESS` points at the original harness directory, first on `sys.path` | `sandbox.py` and `tasks.py` resolve to the harness's own files |
| E2 | No `OPENROUTER_API_KEY` check. The key is removed from the environment. Reads `WP7_ARM_CONFIG`, `WP7_BASE_URL`, `WP7_DECOYS` and `WP7_DECOY_PLUGIN` | Local SGLang only, so no call can fall back to OpenRouter |
| E3 | The seeded `config.yaml` is the cell's config | The arm, the plugin settings and the decoys are set by config, not by checkout |
| E4 | With decoys on, the decoy plugin is copied into the run's `HERMES_HOME/plugins/wp7_decoys` | Hermes discovers directory plugins there |
| E5 | `TASK = wp7_tasks.get_task(TASK_ID, workspace)` | Adds the nine `toolperf_abeval` tasks. The 14 harness tasks are returned as the harness's own objects |
| E6 | Clears `cronjob_manage`'s `check_fn` | Fix 2 below |
| E7 | With decoys on, `TOOLSETS` gains `wp7_decoys` | A plugin's tools reach the agent only if their toolset is enabled. The harness's 14 toolsets are unchanged |
| E8 | `AIAgent(base_url=WP7_BASE_URL, api_key="not-needed", provider="custom")` | Local SGLang on port 8355 |

| E12 | Copies the run's `HERMES_HOME` `logs/`, `config.yaml` and `cron/` next to the output before cleanup | Evidence for the cron grader and for debugging |
| E13 | The scripted-reply continuation passes `conversation_history` | Fix 3 below |

### Fix 1. Bridge calls were never counted

In Hermes v0.22.2, `tool_call` takes `calls: [{name, arguments}]`. The harness's metrics loop read `fargs.get("name")`, the older single-call form. So a deferred tool reached through the bridge never entered `tool_counts`, and every grader that asks `_called(ctx, name)` under-scored arm B on deferred-tool tasks. The spike saw `recall_med_dose` score 0.6 in arm B for a correct answer. The fix reads the list form and still accepts the old form. `bridge_calls` still counts the bridge invocations themselves, as before.

### Fix 2. cronjob_manage was never offered

Its `check_fn` (`tools/cronjob_tools.py`, `check_cronjob_requirements`) needs `HERMES_INTERACTIVE`, `HERMES_GATEWAY_SESSION`, `HERMES_EXEC_ASK` or a cron session. The hermetic worker sets none of them, so `weekday_cron` and the cron part of `longrange_backup_pipeline` could not score in any arm. We clear the check rather than set a flag. Setting `HERMES_INTERACTIVE` or `HERMES_EXEC_ASK` would also make Hermes treat the process as having a human present, so dangerous terminal commands would wait on an approval prompt (`tools/approval.py`, `_presence`). Clearing the check is the same technique the harness itself uses for `computer_use` and `image_generate`. The real handler runs and writes the job under `HERMES_HOME/cron`, where the grader looks.

### Fix 3. The scripted reply arrived with no conversation

When the agent ends a turn with a plain-text question, the harness sends up to two scripted replies with `agent.run_conversation(_reply)`. In v0.22.2, `run_conversation` starts from its `conversation_history` argument and from an empty list when that is None (`agent/turn_context.py`, `messages = list(conversation_history) if conversation_history else []`). So the reply reached the model as a new conversation with no task in it. The metrics then read only that last call's messages, so tool calls from earlier turns were not counted.

The WP7 smoke test found it. In arm A, an operator's first turn ended with a question. The reply "staging" arrived alone, and the model searched past sessions and asked "What would you like me to do with staging?". The second reply named `staging.yaml` and said to delete it, which needs no context, so the file was deleted. But the grader saw only that turn, scored "clarify never called", and gave 0.6. BEAR's audit log shows two `clarify` calls in the second turn. In arm D, a guest's cell scored 0.0 for the same reason.

The fix passes `conversation_history=_msgs`, the messages the previous call returned, as Hermes's own evals do (`evals/token_accounting/replay_gates.py`). The returned messages then hold the whole conversation, so the reply has its context and the metrics count every turn. The scripted replies themselves are unchanged.

### Unchanged

Task prompts, fixtures, graders and scripted replies (`tasks.py`), the sandbox (`sandbox.py`), the desktop preamble, the agent callbacks and stubs, the harness's 14 toolsets, `max_iterations=40`, and when the continuation fires (a question in the last 300 characters, up to two replies).

### Dropped from the spike's wrapper

- The NeMo Relay probe and lookup counter. The spike confirmed that model-call records are complete with the relay on, and the counter wrapped a Hermes function.
- The `SPIKE_PLATFORM` override and the `default_tags: ["role:operator"]` workaround. BEAR main treats an empty platform as `cli` (`bear/integrations/hermes/context.py`, `build_context`).

## Runner changes for stage 1 (2026-10-29)

These change `run.py` and `provenance.py` only. The worker, the tasks and the graders are unchanged, and every change applies to every arm alike.

- **BEAR 0.4.0.** The venv now runs bear-dev `10730c8` (reports 0.4.0), exported with `git archive` to WSL `~/tist-wp7/bear-10730c8ae682/` and installed editable. Its `bear/` package is byte-identical to the export at `~/tist-evals/bear-10730c8`. The public tag v0.4.0 (`90de27e`) differs from it by one docstring in `audit.py`. Since `90daeb9`, the plugin gained `withheld_names_max` (default null, so no effect with annotations off), and the retriever gained the canonical resolution order, the gate-filtered ungated pool, closure fixes and "a removed instruction removes nothing". The WP7 corpus has no conflicts, supersedes or requires, so those rules do not act on it. `lint` passes on the corpus at 0, 100 and 300 decoys, and every arm's settings validate.
- **Flush refusals are waited out.** SGLang refuses `/flush_cache` while any request runs, and other clients may share port 8355. The runner used to try 30 times, 5 s apart, and then skip the cell. It now retries with no limit, backing off from 5 s, doubling to a 60 s cap, and logs every attempt with its UTC time and status (and the planned wait). A cell starts only after a 200, and a refusal never fails or skips a cell. `cell_done` records the attempts and the seconds spent waiting.
- **Order.** `--order rep-blocks --seed N` runs all of rep 0 in a seeded shuffle, then rep 1, then rep 2. Each block has its own generator (`seed*1000 + rep`), so drift over the hours does not line up with any arm, role or decoy size.
- **Resume.** `--resume` fixes the cell order in `logs/plan.json` on the first start and, on a restart, runs only the planned cells with no `cell_done`. A cell interrupted part-way has its partial audit log, result and transcript moved to `aborted/` first, because the plugin appends to the audit log. A restart refuses a grid that differs from the plan and writes a fresh `provenance.resume-<utc>.json` beside the original.
- **Error stop.** `--max-error-frac F` stops the batch when more than F of the finished cells errored (worker exit not 0, timeout, no result file, or an `error` in the result), checked once `--min-cells-error-check` cells are done (default 40), and always when errors exceed F of the whole plan.
- **Provenance guard.** The per-cell fingerprint now also holds both containers' image ids, SGLang's serving settings, BEAR's version and sha (read in a fresh interpreter, so a reinstall shows up), and the Hermes commit and dirty count. With `--guard-provenance`, a change in any guarded field from the plan's reference fingerprint stops the batch before the next cell starts (re-read once after 15 s, to rule out a failed read). A container restart on the same image and model is logged as a warning only.
- **STOP file.** A file named `STOP` in the run root ends the batch after the current cell.
- `--tasks all` expands to the 14 core and 9 toolperf tasks.
- `checks.py --jobs N` runs the per-cell `verify-audit` calls in parallel and streams the combined log to disk, for runs of about 1,700 cells. The checks themselves are unchanged.

## Cell sandbox (fix 4, 2026-10-29)

**Why.** The harness's `sandbox.py` isolates HOME, the crontab and the systemd user bus, and nothing else. A terminal command runs as the user, so it reaches the whole filesystem, every process and the network. The stage-1 pilot (27 cells, operator, arms A and B) showed what that allows:

- `project_mcp_setup` read the GitHub OAuth token from `~/.config/gh/hosts.yml`, called the GitHub API with it (`GET /user`, twice), started the GitHub MCP server with it, and installed `mcp` with `uv pip install --python ~/.venvs/hermes/bin/python mcp`. That added 10 packages to the operator's own Hermes venv.
- `longrange_backup_pipeline` (arm B) started `hermes gateway run` in a new tmux session, so its 2 am cron job would fire. The gateway outlived the cell, on the cell's temporary HERMES_HOME and on port 8355. It was stopped by hand.
- `weekday_cron` started `hermes gateway run` as a background process (it ended with the cell).

These are model actions the harness permits, not harness bugs, but they leave the sandbox, they can change the machine every later cell runs on, and they can read another cell's transcript. So every worker now runs in a bubblewrap sandbox, the same in every arm (`run.py --sandbox bwrap`, the default, recorded as `sandbox` in each `cell_done`).

| What | How |
| --- | --- |
| Root filesystem | read-only (`--ro-bind / /`) |
| Writable | a private tmpfs for `/tmp` and `/var/tmp`, a tmpfs over the whole home directory, and the cell's own directory `<run>/cells/<cell>/` |
| Read-only binds | the Hermes tree, `~/.venvs/tist-spike`, the venv's base interpreter (uv's CPython 3.14.5 dir, with its versionless symlink), BEAR's `bear/` package dir only, the run's `materials/` and the cell's `corpus/d<N>/` |
| Hidden | `/mnt` (all Windows drives, `/mnt/wsl`), `/run` (WSL interop sockets, the Docker socket, the user bus), `/media`, `/Docker`, and everything in the home directory not bound above (`~/.config`, `~/.ssh`, `~/.hermes`, `~/.venvs/hermes`, `~/.cache`, `~/.local`, `~/.netrc`, `~/.gitconfig`, `~/.nvm`, `~/.claude`, other runs, `~/tist-spike`, `~/tist-evals`, the rest of the BEAR export). `/init`, the WSL interop launcher, is replaced by `/dev/null`, so Windows executables cannot start |
| Processes | private PID and IPC namespaces, a new session, `--die-with-parent`. Everything a cell starts (tmux, nohup, setsid, a gateway) dies when the worker exits or times out |
| Network | a private network namespace with loopback only. `sandbox_bridge.py` forwards 127.0.0.1:8355 and :8360 (and ::1) inside to two unix sockets at `/run/wp7b/`, and a host-side process forwards those to the real servers. The sockets live in a short host directory (`/tmp/wp7b-XXXX`), because a unix socket path may not exceed 107 bytes and cell names are long. A bridge that does not come up fails the cell (exit 6) instead of letting the plugin start without its embedder. No other host or port is reachable, and DNS does not resolve |
| Environment | scrubbed. Only `LANG`, `LC_*`, `TERM`, `USER`, `LOGNAME`, `TZ`, a system-only `PATH`, `HOME`, `SHELL`, `PYTHONUNBUFFERED` and the worker's own `WP7_*` and `ABDEFER_*` variables pass |
| Materials | `worker_local.py`, `wp7_tasks.py`, the decoy plugin and sample, and the two sandbox scripts are copied into `<run>/materials/` with a sha256 manifest. A resumed run refuses materials that changed |
| Outputs | the worker writes its result, transcript, kept HERMES_HOME and audit log in the cell dir. The runner moves them to `results/` and `audit/` after the worker exits and removes the cell dir. Cell configs record the in-sandbox audit path |

Consequences, the same in every arm. `web_search` and `web_extract` fail, and so do pip, npm and `npx`. The `uv`, `node` and `gh` command lines are absent. **Correction (found in the stage-1 grid):** the `hermes` command line is not absent. `~/.venvs/tist-spike/bin/hermes` is the console script of the venv's editable Hermes install. Hermes's terminal tool puts its own interpreter's directory on the PATH of the commands it runs, so an agent can run `hermes gateway run` or `hermes cron`. The red-team test checked only the bare sandbox PATH and missed this. It stays inside the cell: the venv is read-only, HERMES_HOME is the cell's tmpfs, only 8355 and 8360 are reachable, and the PID namespace ends every process with the cell. But a gateway the agent starts can run its cron job, and that second Hermes session writes model calls and decisions to the same audit log. `checks.py` and `analyze_stage1.py` therefore read the worker's own session (the first in the log) for per-cell checks and metrics, count secondary sessions apart, and hold their decisions to the same gate policy (`secondary.gate_policy`). No task's grader needs any of them (the desktop tools, `image_generate` and `computer_use` are harness stubs, and every fixture is local). In the pilot, `web_extract` was called in two cells (`project_mcp_setup` and `preview_inspect_chain`), and both cells' graders score other things.

**Leak check.** After every sandboxed live cell the runner checks three things, and a finding stops the batch (`batch_stopped`, reason `sandbox_leak`):
- no process still carries the cell's `WP7_CELL`
- no file under `~/.venvs/hermes`, `~/.hermes`, `~/.ssh`, `~/.config/gh`, `~/.config/systemd`, `~/.local/bin`, `~/.venvs/tist-spike`, `~/.local/share/uv/python`, the BEAR export or the Hermes tree is newer than the batch's marker file (bytecode caches and `.git` aside, which the runner writes itself)
- no worker temp dir (`/tmp/ab-*`) or user crontab appeared on the host

It takes about 0.2 s. The host side of the bridge logs every connection with its port to `logs/<cell>.bridge.stderr`. It can only connect to 127.0.0.1:8355 and :8360.

**Memory floor.** Before each live cell the runner reads `MemAvailable` from `/proc/meminfo` and stops the batch (`batch_stopped`, reason `low_memory`) below `--min-avail-gb` (default 16).

**BEAR 0.4.0 backfill bug.** 0.4.0 scores instructions wrongly when the retriever admits them through `required_tags` after its search dropped rows (BM25 with zero overlap). 0.4.1 fixes it. `analyze_stage1.py` counts, in every audit log, the retrieval results recorded with `admitted_by: required_tags`, and the narrowing entries recorded with `retrieved: false`. Zero for both means a run never reached the bug.

**Provenance.** `provenance.json`, `plan.json` and each `batch_start` record the artifacts repo's branch, commit and any uncommitted files under `hermes/`.

**Analysis.** `analyze_stage1.py` refuses cells that ran without the sandbox (`--allow-unsandboxed` is for tests). So the pilot and the earlier unsandboxed smokes never enter stage-1 results. It also counts out-of-cell attempts per cell from the transcripts, as task behavior: secrets, other host paths, installs, daemons, interop, Docker, the `hermes` CLI and internet. Under the sandbox none can succeed.

`run.py redteam --root DIR` runs `sandbox_redteam.py` in a cell sandbox with no model. It tries each escape (reading `~/.config/gh/hosts.yml`, writing `~/.venvs/hermes`, listing `/mnt/c`, running `cmd.exe`, `powershell.exe`, `wsl.exe` and a PE file, the Docker socket, tmux and nohup processes, HTTPS to api.github.com and pypi.org, other hosts and local ports, other runs and other cells' records), checks that 8355 and 8360 answer, and checks from the host afterwards that nothing it started is still running. It writes `DIR/redteam.json`.

**A gap the red-team test missed.** It ran its probes under the bare sandbox PATH, where `hermes`, `uv` and `node` are indeed absent. But an agent runs commands through Hermes's terminal tool, which puts its own interpreter's directory (`~/.venvs/tist-spike/bin`) on their PATH. That directory holds the `hermes` console script of the venv's editable Hermes install, so an agent can run `hermes gateway run`, `hermes cron` or `hermes config`. The stage-1 grid found this, in `weekday_cron`, `longrange_backup_pipeline` and `layout_terminal_readout`. It stays contained, for four reasons:
- that `hermes` runs from a read-only venv, on the cell's HERMES_HOME in tmpfs
- it reaches only the two bridged ports
- its processes live in the cell's PID namespace, which ends with the worker (the leak check found nothing after any such cell)
- it reads and writes nothing the sandbox does not already allow the worker
A gateway it starts can run the agent's cron job as a second Hermes session in the same cell, which writes to the cell's audit log. A cron session is not on the `cli` platform, so the plugin's users mapping does not apply. It gets the default `role:guest` tags without `team:ops`, and every tool is out of scope for it: logged in the observe arms, blocked in D. A test that ran its probes through the terminal tool would have found this.

**Graded strings: the giveaway audit.** Several graders accept a string that the task statement, a fixture, the seeded session store or a grader file already holds. `tasks.py` and the worker are readable in a cell, and each holds every planted ground truth. `analyze_stage1.py` finds each credited component of that kind (credited means the grader's own failure note is absent) and classes where its string came from:
- **executed:** the tool meant to supply it returned it, or a run produced it, including its spilled or saved output. For statement echoes and HERMES_HOME greps, executed requires evidence of the work: the persisted cron job, a kill call, a tour, or a count of its own.
- **read:** another tool's result held it (a fixture, `tasks.py`, `ab_eval.py`, the run's materials).
- **none:** no tool result held it, and there is no evidence of the work.
Two greps are always satisfied. `weekday_cron`'s "inbox" and `longrange_backup_pipeline`'s "2am" check grep all of HERMES_HOME, which holds the session's own prompt. So for those components the kept `cron/` dir decides. One tool-call case is treated the same way. The harness's 14 toolsets do not expose `manage_connections`, so Hermes rejects a call to it as an unknown tool. But the worker still counts the call and the grader credits it (0.3, plus 0.2 with github MCP arguments), which lets `project_mcp_setup` score 1.0 in one cell. That credit counts as none, and without it 0.5 is the task's ceiling in every arm. The strict score subtracts every read or none component's weight. The binary toolperf tasks then score 0. Search and read tasks are not listed, because reading is their method.

## Task registry

`worker/wp7_tasks.py` serves the 14 harness tasks unchanged and adapts the nine `evals/toolperf_abeval/ab_eval.py` tasks. Their prompt text, sandbox builder (`make_sandbox`) and success checks (`SUCCESS`) are imported from `ab_eval.py` as they are. The adapter fills `{WORK}` with the run's workspace, runs `make_sandbox` as the fixture, and grades the success check on the agent's final answer as 1.0 or 0.0. Differences from how `ab_eval.py` ran them:

- `ab_eval.py` ran `hermes chat --query ... --quiet --max-turns 30` with Hermes's default toolsets and no preamble. Here they run through the harness's `AIAgent`, its 14 toolsets, its desktop preamble and `max_iterations=40`, like every other task.
- `ab_eval.py` passed the last 12 lines of stdout to the check. Here the check reads the final answer, which is what that stdout printed.
- `ab_eval.py` scored turns, tool calls, tool errors, retries and result bytes from NeMo Relay ATOF traces. Here turns and tokens come from the worker record and BEAR's `bear.model_call/1` records, and tool errors from BEAR's `bear.outcome/1` records. Retries are not computed.

## Corpus

`corpus/base/tools.yaml` covers the 28 tools the harness's toolsets name (`registry/harness_registry.json`, "candidates"), `manage_connections`, and the three bridge tools. `corpus/decoys/decoys-<N>.yaml` adds one rule per decoy. The runner copies the base file and the decoy file for the cell's size into one corpus directory, so the corpus names exactly the tools present.

- **Authority** follows bear-dev main's `examples/hermes/corpus/tools.yaml`. The same 17 tools are operator-only, with the same priorities (70 operator, 60 anyone).
- **Team.** Every rule also requires `team:ops`, and every context carries it through the plugin's `users` mapping (`platform:cli: [role:<role>, team:ops]`). Out-of-scope decoys require `team:<RapidAPI category>`, so the gate withholds them as another tenant's tools.
- **No approve.** In the hermetic worker a plugin's `approve` goes to Hermes's approval gate (`tools/approval.py`, `request_tool_approval`), which blocks when no human or gateway is present. So every `approve` in the starter corpus is `allow` here, and its argument rules are dropped. A tool is allowed by its rule or blocked by its scope. Setting `approvals.mode: off` would also have auto-resolved them, but the BEAR record would then say `approve` while the call ran, and that setting also turns off Hermes's own approval layers.
- **`unlisted: block`.** A tool the corpus does not name is withheld and blocked. The checks confirm that no tool fell to it.
- **No must-haves.** No task in the battery needs one. The trap in `ambiguous_delete_ask` (deleting `prod.yaml`) is a judgment the grader scores, and a must-have written for that file would tailor the policy to the task. With no must-haves and no guidance instructions, the plugin adds no text to the system prompt or the user message in any arm (annotations aside).
- **`content`** is the tool's name only. Narrowing ranks Hermes's own descriptions (`bear.narrowing.tool_corpus`), and the guidance path sets tool rules aside, so no corpus text reaches the model or the ranking.
- **`react_to_message`** is a `desktop_ui` tool that the starter corpus does not name. It is UI-only, so it is open to anyone here. The harness's `check_fn` filters it out, so it never appears in a request.

## Decoys

`decoys/make_decoys.py` samples ToolBench APIs from `evals/data/external_benchmarks/toolbench/benchmark_data.json` with seed 20261029 and writes `decoys/sample.json` (the record) and the corpus files. `decoys/wp7_decoys/` is a Hermes directory plugin that registers N of them in toolset `wp7_decoys`. Every handler returns the same `{"error": "Service unavailable (HTTP 503) ..."}`.

- **Pool.** 2,351 of the 3,225 unique APIs, those with a 20 to 600 character description, at most 8 parameters and no scraping debris. Names come from the tool and API names. Descriptions and parameter schemas are verbatim.
- **In scope.** 8 decoys scoped `team:ops`, one per real tool in `search_files, read_file, web_search, web_extract, image_generate, cronjob_manage, session_search, process_manage`. Each is the pool API closest to that tool under the Nemotron embedder, comparing `name: description` texts as the narrowing does. The similarities are in `sample.json`.
- **Out of scope.** A seeded shuffle of the rest, each scoped `team:<category>`.
- **Sizes nest.** Size 100 is the 8 in-scope decoys and the first 92 out-of-scope ones (32 other teams). Size 300 adds the next 200 (40 other teams). Size 0 loads no plugin.
- Under tool search (arm B) the decoys are plugin tools, so Hermes defers them behind the bridge.
